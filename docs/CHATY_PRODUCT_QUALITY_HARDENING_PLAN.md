# Chaty Product Quality & Security Hardening Plan

Target branch: `kotlin`
Baseline commit: `8624fe2923ab33ec7cb582b89e976dbdab71ca46`
Policy: additive changes only. Do not delete or silently disable existing user-facing features, persisted user data, routes, or component variants. Any replacement must preserve old behavior behind a compatible adapter and include regression coverage.

## 0. Release gate: restore a reproducible build
- Reproduce and fix every Kotlin compiler error before feature work is merged.
- Latest observed CI run: 41267339116; backend ICE route syntax passed; Android `:app:compileDebugKotlin` failed.
- Reported compile failures: LockBadgeProofActivity ChatyIcon invocation + syntax, VoiceGestureFixtureActivity pause/resume overrides, AacPcmVoiceRecorder pause/resume overrides, ServiceLocator Firebase Messaging unresolved references, VoiceSessionController missing togglePause/isPaused.
- Important: several failing sources are restored/generated by the CI candidate overlay, not directly present at their generated paths in the branch. Fix the authoritative overlay source or the workflow patch, not a transient generated file.
- Add compile + unit tests + instrumentation smoke checks; no APK release until all required gates pass.

## 1. Call experience: consent-gated screen sharing
- Keep screen share visible only in an accepted, active video call with local media and a live video sender.
- Start sharing only after Android MediaProjection system consent returns RESULT_OK with a non-null result Intent.
- On cancel, denial, call end, account switch, activity recreation, or projection revocation: do not start / stop capture and restore the camera track.
- Guard permission results and start/stop actions by callId + account scope to prevent a stale activity result affecting a later call.
- Add clear state labels (requesting, sharing, stopped, failed), accessibility descriptions, and tests for accepted/incoming/voice/denied/cancelled/revoked states.
- Keep microphone audio active; never silently start screen capture.

## 2. Media selection and large videos
- Audit every entry point: gallery, camera capture, file picker, document picker, forwarded media, status/story, profile media, and chat attachments.
- Use Android Photo Picker / SAF URI grants; avoid broad storage permissions when not needed.
- Preserve original URI, display name, MIME, size, duration, orientation and persisted read permission. Avoid whole-file copies into cache and ByteArray loading.
- Long videos: stream file descriptors in bounded buffers, support large sizes and low free storage, expose duration/size, show upload/transfer progress, retry/cancel, and resume where protocol supports it.
- Keep video selection in the normal attachment tray and show a native video message card with a real thumbnail/duration; never render an attachment as a bare URL.
- Enforce configurable limits only where backend/protocol limits require them; explain limits before selection/send. Do not silently truncate or recompress.

## 3. End-to-end encryption and privacy
- Map every content path: text, edits, replies, reactions, files, photos, video, voice notes, calls, screen-share media, backups, notifications, search, previews and thumbnails.
- Require MLS group readiness and fail closed; never fallback to plaintext. Verify membership/epoch and device key lifecycle.
- Encrypt attachment bytes client-side with per-attachment keys derived from MLS exporter material; authenticate metadata and bind conversationId + attachmentId as AAD. Keep keys out of URLs, logs, push payloads and backend storage.
- WebRTC uses DTLS-SRTP for transport encryption; document its threat model separately from MLS message E2EE. TURN relays must never receive media plaintext.
- Verify encrypted thumbnails/previews and temp-file cleanup; exclude decrypted content from backups, logs and crash reports.
- Current code contains MLS and encrypted P2P primitives, but the Kotlin MLS adapter and all media upload/download paths require an end-to-end audit before claiming every path is E2EE.

## 4. Remove mock-only behavior without losing design previews
- Inventory every button, setting, menu, route and feature flag against a real action, persisted preference or backend operation.
- Replace production demo fallbacks with explicit empty states. Keep preview/demo fixtures only in debug builds or isolated preview/test providers.
- Settings must read/write the same source of truth as the feature they control; show unavailable/not configured when backend capability is absent.
- Add a settings wiring matrix and tests for persistence, restart, account switching and permission denial.

## 5. Performance and reliability
- Profile cold start, home/chat scrolling, message composition, media picker, video playback, calls, settings and background sync on low/mid-range Android.
- Remove main-thread disk/network/thumbnail work; use bounded IO dispatchers, paging/windowing, stable Compose keys, derived state, lazy media loading and cancellation.
- Cache thumbnails by content identity + dimensions; bound memory/disk cache; avoid repeated decode and duplicate collectors.
- Optimize WebRTC/transfer by measured bandwidth, congestion/backpressure, bounded queues, retry with jitter, durable transfer journal and receiver integrity verification.
- Add baseline profiles, Macrobenchmark, StrictMode debug checks, leak checks and battery/network measurements.

## 6. Product and interaction audit
- Build a component inventory and screen-flow map for all modules, including WhatsApp-like chat/calls/status, Telegram-like channels/files, Snapchat-like camera/effects, Instagram-like stories/reels/profile/media.
- For every component verify loading, empty, error, offline, permission-denied, disabled, selected, pressed, focus, accessibility and large-font states.
- Apply Apple HIG and Android Material guidance where relevant: hierarchy, consistency, direct manipulation, predictable navigation, safe areas, touch targets, typography, contrast, motion restraint, undo/destructive confirmation, privacy prompts and permission timing.
- Use user intent and task completion as the test: send a long video, resume a transfer, answer a call, share screen, recover after network loss, change a setting, and verify it survives restart.

## 7. Play Protect / release integrity
- Do not hide app identity, obfuscate behavior to evade scanning, disable verification, or manipulate package metadata to bypass Play Protect.
- Inspect signing certificate continuity, debug-vs-release signing, dependency provenance, manifest permissions, exported components, network cleartext, native libraries, dynamic code loading, downloaded executable code, trackers and build reproducibility.
- Use a stable release signing key, Play App Signing where applicable, SBOM/dependency scanning, malware scanning, reproducible CI artifacts and Play Console policy checks.
- Diagnose the exact Play Protect warning and affected APK hash/version before attributing a cause. A false positive requires a clean, signed build and Google's review/reporting process.

## 8. Acceptance criteria
- No removed screens/features or lost user data; old persisted settings migrate safely.
- Clean release and debug builds; unit + instrumentation tests pass.
- Screen share requires explicit system consent and stops on revocation/end.
- Long-video selection/send/receive works without loading entire media into RAM; progress and failure/retry states are truthful.
- All content paths have a documented encryption boundary and tests; no plaintext fallback.
- No production-only demo data or inert settings controls.
- Performance regressions are measured against baseline on a low/mid-range device.
- Play Protect diagnosis is evidence-based and no bypass mechanisms are introduced.
